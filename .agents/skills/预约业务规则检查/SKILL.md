# 宠物门店预约业务规则检查

## 用途

依据原始题面、R-01～R-12 和已确认 A-01～A-12，检查实现或设计是否破坏预约、名额、履约与资金的一致性。本 Skill 只提供检查结论，不替代真实测试、数据库证据或学生确认。

## 触发场景

- 设计数据库状态、事务或接口前；
- 完成预约、支付、取消、退款、履约或日清模块后；
- 修改关键状态流转或并发控制后；
- 测试发现名额、状态或金额不一致时；
- 开发 Agent 准备交给测试 Agent 前。

## 输入

至少提供：

1. 原始题面和当前确认的需求/假设文件路径；
2. 本次检查的任务编号与范围；
3. 对应代码、迁移、接口或设计文件路径；
4. 当前提交哈希；无提交时明确写“未提交”；
5. 已执行测试及原始结果位置；没有时明确写“无”。

输入不足时不得推测通过，应列为 `BLOCKED` 或 `NOT_EVIDENCED`。

## 执行步骤

1. 读取原始题面题目 02、`需求说明.md`、`假设与待确认事项.md` 和 `AGENTS.md`。
2. 确认范围对应 R/S/T 编号，列出本次不检查的内容。
3. 检查容量与唯一性：
   - 一预约一宠物，容量按宠物计；
   - 同宠物同时段至多一个有效预约；
   - 待支付未过期、已确认、取消待审核及履约中按规则占位；
   - 并发不能超过容量，释放名额只能一次。
4. 检查时间规则：
   - 占位 5 分钟，服务端时间为准；
   - 恰好提前 2 小时自动取消；不足 2 小时且未开始需审核；开始后禁止申请；
   - UTC 持久化，按 `Asia/Shanghai` 计算业务边界；教学时钟仅限测试/演示配置。
5. 检查支付与退款：
   - 金额固定 9900 分且使用整数；
   - 请求、通知、退款单和尝试编号具备数据库幂等约束；
   - 关闭后晚到支付不恢复预约并产生退回处理；
   - 超时为待确认；取消与退款状态独立；退款失败不恢复预约。
6. 检查取消与履约：
   - 审核期间继续占位并禁止核销；
   - 拒绝后可新建申请但同时最多一个待审核；
   - 核销与取消竞争只有一个合法结果；
   - 核销→服务开始→完成顺序不可跳跃，重复操作不重复确认收入。
7. 检查权限：用户/宠物、员工角色、门店归属均由服务端可信身份校验；外部门店员工被拒绝。
8. 检查未到店和日清：结束后才能标记且原因必填；不自动退款；已收、已退、未退、完成收入分别从事实记录计算并可下钻。
9. 对每项给出 `PASS`、`FAIL`、`NOT_EVIDENCED` 或 `NOT_APPLICABLE`，引用文件、行、测试或命令证据。
10. 若发现问题，生成最小修正建议和受影响复测清单；修正后使用同一检查编号重新执行并对比前后结果。

## 失败处理

- 题面或需求文件缺失：停止检查并列出缺失输入。
- 代码与测试版本不一致：标记版本不一致，不沿用旧测试结论。
- MySQL/并发测试未执行：相关并发项标记 `NOT_EVIDENCED`，不得按代码阅读判通过。
- 发现密钥、越权、超额占位、重复金额或非法状态组合：列为阻断问题，禁止进入测试交接或发布。
- 工具命令失败：保留原始错误，不能伪造替代结果。

## 完成标准

- 输入和版本明确；
- 所有本次适用规则逐项有结论和证据；
- 无未处理的阻断级 `FAIL`；
- `NOT_EVIDENCED` 均有明确补证任务，交接前关键项不得残留；
- 发现的问题具有修正要求和复测清单；
- 复查结果保留首次问题，不覆盖历史。
