# 题目 02 验收检查

## 用途

依据教师原始题面检查最终版本是否满足完整业务闭环和第一部分通用要求，输出可审计的逐项结论。本 Skill 不接受开发 Agent 的完成声明作为证据。

## 触发场景

- 独立验收 Agent 开始验收时；
- 测试缺陷全部复测后；
- PR 创建或合并前；
- 验收后修改业务代码需要重新验收时；
- 正式部署与最终提交材料复核时。

## 输入

1. 原始题面文件；
2. 最终代码仓库、分支和精确提交哈希；
3. 需求、假设、原型、任务和追踪表；
4. 单元测试、覆盖率、MySQL 集成测试、接口、并发/race 原始结果；
5. 缺陷、修复、复测记录；
6. `AGENTS.md` 历史与实际读取记录；
7. 自编及既有 Skill 文件、调用输出和 `skill-usage.md`；
8. GitHub MCP、工作项核验、分支、提交、PR、保护规则证据；
9. CI/CD、部署提交、地址、健康和业务冒烟证据；
10. AI 会话 Markdown、JSON/JSONL 事件和 AI 使用说明。

缺少的材料必须列明，不得用口头解释补成证据。

## 执行步骤

1. 确认验收 Agent 使用独立会话，并读取原始题面而非开发摘要。
2. 锁定验收提交哈希，核对代码、测试、报告和后续部署是否对应同一可追踪版本。
3. 逐项验收 R-01～R-12，检查实际页面、接口、数据库结果、权限和错误原因。
4. 逐项执行或核验 S-01～S-05：正常接待、名额循环、取消分支、现场冲突、收店核查。
5. 检查数据一致性：名额不超限且只释放一次；业务状态、支付、退款、履约和日清金额一致；重复及并发操作幂等。
6. 检查权限与安全：本人宠物、本店员工、角色职责、可信身份、敏感信息和日志脱敏。
7. 检查质量门禁：整体和每个核心包单元语句覆盖率均 `>=85%`；`gofmt`、`go vet`、测试、真实 MySQL 集成、并发及 `go test -race` 有原始结果。
8. 检查流程证据：需求→原型→计划→开发→独立测试→独立验收→自动部署顺序真实；缺陷修复后有复测；没有结束时补造记录。
9. 检查 Git：MCP 建仓证据、`dev/02`、真实编号核验、规范提交、PR、main 保护和合并后门禁。已知缺失必须判为缺口，不得豁免。
10. 检查 Skill 与 AI 记录：两个自编 Skill 结构完整且实际调用；至少一次问题发现/修正/复查或真实无问题记录；导出与说明完整。
11. 检查部署：只发布 PR 合并后的 `main` 实际提交；流水线包含规定步骤；服务可访问；部署版本、冒烟和回退方案可核查。
12. 汇总阻断项、一般问题、补证项和最终结论。任何关键业务、覆盖率、Skill、AI 追踪、部署、Git 流程、群提交或视频要求不通过时，不得判整题通过。

## 失败处理

- 无法锁定版本：停止业务结论，要求提供精确提交。
- 服务、数据库或依赖不可用：记录实际错误和阻塞范围，不编造执行结果。
- 测试、部署或 Git 证据只来自自述：判 `NOT_EVIDENCED` 或 `FAIL`。
- 验收发现缺陷：登记真实缺陷，交回开发修复；受影响测试和验收全部重新执行。
- 验收后代码变化：旧验收结论对变化范围失效。
- 敏感信息泄露：立即列为阻断问题并要求轮换、清理和复核历史。

## 完成标准

- 原始题面、最终代码和精确版本均已读取；
- R-01～R-12、S-01～S-05 和全部通用门禁逐项有真实证据；
- 所有阻断项关闭并有复测/复验记录；
- 最终部署与验收版本可追踪一致；
- 报告明确区分通过、失败、阻塞和未举证；
- 只有全部必过要求满足时才输出“通过”。
