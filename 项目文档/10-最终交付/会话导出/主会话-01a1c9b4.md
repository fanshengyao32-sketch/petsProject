## 题目 02：宠物门店的预约、接待、服务与取消退款

**岗位来源**：[小布网络科技｜高级go开发工程师](https://www.zhipin.com/job_detail/239f71cea3efbaf90nx42dq_E1BT.html)。CSV 职责摘录：“负责公司宠物 O2O 平台的全栈研发工作”“深入理解预约、下单、支付、退款、营销活动、会员、服务履约等核心业务流程”。

### 业务背景与现场情境

一家宠物护理门店通过 O2O 平台接受洗护预约。店长安排服务时段，宠物主人选择时段并支付预约款，前台负责到店核验，服务人员登记服务完成，平台客服处理取消和退款。门店希望提前知道每个时段会来多少宠物，用户则希望预约结果、付款结果和实际服务相互对应。

周六下午的时段很紧张，同一时间有多位用户争抢最后的名额。有的用户预约后没有付款，有的付款后提前取消，也有人临近开始时间提出取消申请。另一位用户已到店，但同行人员再次点击取消。客服需要根据预约所处环节处理，不能只看“是否付款”；店长收店时也需要分清已服务、已退款、未到店和仍待处理的预约。

请实现这一家门店的预约经营场景，让用户、前台和客服在同一份业务记录上协作，并让店长能够核查一天的预约与收款去向。

### 参与角色与业务起点

- 店长：发布可预约时段、查看预约及经营结果。
- 宠物主人：为宠物预约、付款、取消、查看服务结果。
- 前台及服务人员：核验到店，登记服务开始与完成。
- 客服：审核临近开始时的取消申请，跟进退款失败。
- 模拟支付渠道：返回预约款支付及退款结果。

预置一家门店、一个洗护项目、三个未来时段，每时段最多接待 3 只宠物，预约款即本次服务全款 9900 分；预置用户和宠物资料，不实现档案编辑。

### 需要完成的业务范围与规则

1. 店长创建时段时明确起止时间。用户选择自己的宠物预约，同一宠物同一时段只能有一个有效预约；名额不足或时段已开始时不可预约。
2. 未付款预约占用名额 5 分钟，超时或主动取消后释放。有效付款后成为已确认预约；重复支付通知不得重复确认。关闭后收到支付成功须登记异常并退还款项，不恢复预约。
3. 用户在开始前至少 2 小时取消已确认预约，可全额退款；开始前不足 2 小时须提交原因，由客服批准或拒绝，待审核期间保持名额且不得核销。
4. 取消获准后不得到店核销，名额仅释放一次。退款状态独立可查询，退款失败需要跟进，不能因为退款失败让已取消预约重新可用。
5. 前台只能核销本店、已确认且没有待处理取消申请的预约，随后服务人员可登记开始及完成；重复核销或完成不能重复记收入。
6. 核销与取消同时发生时必须得到唯一合法结果。已核销、服务中或已完成预约不能再走本题取消退款流程。
7. 时段结束后仍未到店的预约，由店长标记未到店并写明原因。本题约定未到店不自动退款，用户可查看这一结果；不实现争议退款裁决。
8. 店长查询当日各时段有效预约、已完成、取消、未到店及退款待处理记录；已收款、已退款与未退款金额须可从记录核查，不能把所有已付款都计作已完成服务。

### 必须演示的完整工作场景

- 正常接待：店长发布时段 → 用户预约付款 → 前台核销 → 服务开始、完成 → 用户与店长查询结果。
- 名额循环：并发预约抢位 → 未付款超时或用户取消 → 名额恢复 → 新用户预约成功。
- 取消分支：提前取消自动受理；临近开始时客服分别批准、拒绝；退款失败后重试；用户能看到各自不同结果。
- 门店现场冲突：同一预约取消与核销并发，重复核销，非本店员工操作，均不能破坏预约和金额记录。
- 收店核查：同一天包含已服务、取消退款、未到店和退款失败四种记录，店长能够分别核查。

### 原型、Skill 与单日边界

原型须覆盖用户预约及订单、前台接待、客服处理、店长日清。业务 Skill 用于检查名额、预约时间、取消政策、服务进度和退款之间的约束。

可以考虑三套组合：

| 方案 | Web 框架 | 数据访问 | 优点 | 不足 |
|---|---|---|---|---|
| A（推荐） | Gin | GORM + PostgreSQL | 开发快、资料多、事务和行锁支持较方便，适合一天交付 | GORM 隐式行为较多，需要明确事务边界 |
| B | Echo | GORM + PostgreSQL | 路由和中间件简洁，错误处理比较统一 | 国内资料和示例略少于 Gin |
| C | Chi | pgx/sqlc + PostgreSQL | 接近标准库、类型明确、业务代码可控 | 样板代码和前期配置更多，一天内压力较大 |

我的推荐组合是：

```text
Gin
+ GORM
+ PostgreSQL
+ html/template
+ 少量 HTMX
+ Docker Compose
+ testify / httptest
```

具体理由：

- Gin：适合快速完成用户端、前台端、客服端和店长端页面及接口。
- GORM：能较快实现事务、条件更新、唯一索引和 `FOR UPDATE` 行锁。
- PostgreSQL：比 SQLite 更适合验证“并发抢最后名额”和“取消与核销竞争”。正式环境和测试环境也能使用相同数据库行为。
- `html/template`：满足最小业务页面要求，不必引入 React/Vue 的构建链。
- HTMX：可选，用于表单提交、状态刷新和操作结果提示；即使不用也不影响项目。
- Docker Compose：统一启动应用、PostgreSQL和模拟支付服务。
- `testify + httptest`：便于写业务单元测试和 HTTP 接口测试。

建议的项目形态：

```text
浏览器页面
    ↓
Gin Handler
    ↓
Application Service（事务和业务流程）
    ↓
Domain（状态、规则、错误）
    ↓
GORM Repository
    ↓
PostgreSQL

Application Service
    ↓
模拟支付 HTTP 服务
```

项目内部按业务划分：

```text
internal/
├── slot/          # 服务时段
├── booking/       # 预约、占位和容量
├── payment/       # 支付及晚到支付
├── cancellation/  # 取消申请和客服审核
├── refund/        # 退款及失败重试
├── fulfillment/   # 核销、服务开始和完成
├── closing/       # 未到店和日清
├── auth/          # 预置账号及角色权限
└── platform/      # 数据库、时钟、审计等基础能力
```

不建议本题使用：

- 微服务：业务规模小，会增加部署和证据整理成本。
- Redis 抢占名额：数据库事务已经足够，Redis 会增加一致性处理。
- Fiber：基于 `fasthttp`，与标准 `net/http` 生态存在差异，本题没有性能收益。
- SQLite：实现简单，但不适合作为并发验收的主要数据库。
- React/Vue：页面要求不复杂，会挤占业务规则和测试时间。
- 完整 DDD/Clean Architecture 模板：容易形成过度设计。

最终建议定为：**Gin + GORM + PostgreSQL + html/template，采用模块化单体架构，模拟支付作为独立 HTTP 进程。**
