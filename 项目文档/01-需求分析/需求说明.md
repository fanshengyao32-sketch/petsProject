## 2. 目标与成功标准

系统需要让店长、宠物主人、前台/服务人员、客服和模拟支付渠道围绕同一份预约记录协作，形成以下闭环：

1. 时段发布与容量控制；
2. 预约占位、付款确认及占位释放；
3. 到店核销、服务开始与完成；
4. 提前取消、临近取消审核及退款跟进；
5. 时段结束后的未到店处理；
6. 店长按日核对预约状态和资金去向。

成功不等同于“页面可用”或“支付成功”。所有指定分支均须可操作、持久化、可追溯，并能说明业务结果与金额结果。

## 3. 角色与权限

| 角色 | 可执行操作 | 关键限制 |
| --- | --- | --- |
| 店长 | 创建本店时段；查看预约；时段结束后标记未到店；查看日清 | 不代替客服审批临近取消；不能在时段结束前标记未到店 |
| 宠物主人 | 为自己的预置宠物预约；发起付款；取消/申请取消；查看预约、退款和服务结果 | 不能操作他人宠物或预约；已核销、服务中、已完成、未到店记录不能走本题取消流程 |
| 前台 | 核验本店符合条件的预约 | 不能核销其他门店、非已确认、有待处理取消、已取消或已核销的预约 |
| 服务人员 | 对已核销预约登记服务开始、服务完成 | 必须按顺序流转；重复操作不得重复记收入 |
| 客服 | 审批临近开始的取消申请；跟进及重试退款失败记录 | 不能审批非待审核申请；拒绝取消后预约仍有效 |
| 模拟支付渠道 | 返回支付和退款结果，支持成功、失败、超时/待确认、重复通知 | 回调必须鉴权并按业务请求唯一标识幂等；不能直接修改服务状态 |

身份必须由可信认证信息确定，不能通过修改请求中的用户编号、门店编号或角色字段越权。

## 4. 核心业务对象

| 对象 | 关键内容 |
| --- | --- |
| 门店 | 门店编号、名称 |
| 洗护项目 | 项目编号、名称、固定价格 9900 分 |

| 服务时段 | 门店、项目、开始/结束时间、容量、状态 |
| 预约 | 用户、宠物、时段、金额、占位截止时间、预约主状态、版本号 |
| 支付单 | 支付请求号、渠道交易号、金额、状态、回调记录 |
| 取消申请 | 申请人、原因、申请时间、是否临近取消、审核状态及意见 |
| 退款单 | 退款请求号、关联支付单、金额、状态、失败原因、重试记录 |
| 履约记录 | 核销、服务开始、服务完成的操作人和时间 |
| 未到店记录 | 标记人、标记时间、原因 |
| 审计/异常记录 | 越权、非法流转、晚到支付成功、重复通知、并发冲突等 |

## 5. 预约生命周期

建议以预约主状态表达业务阶段，以支付、取消、退款子状态表达独立事实，避免一个状态同时混合履约和资金语义。

### 5.1 预约主状态

```text
待支付
  ├─支付成功────────────→ 已确认
  ├─用户主动取消────────→ 已关闭
  └─占位超时────────────→ 已关闭

已确认
  ├─距开始 >= 2 小时取消→ 已取消
  ├─距开始 < 2 小时申请→ 已确认（取消状态=待审核，禁止核销）
  ├─到店核销────────────→ 已核销
  └─时段结束且未到店────→ 未到店

取消待审核
  ├─客服批准────────────→ 已取消
  └─客服拒绝────────────→ 已确认（恢复可核销）

已核销 → 服务中 → 已完成
```

终态或本题不允许继续取消的状态：已取消、已核销、服务中、已完成、未到店、已关闭。

### 5.2 独立资金状态

- 支付状态：待支付、处理中/待确认、成功、失败、异常成功待退回。
- 退款状态：不适用、待退款、退款中、退款成功、退款失败。
- 预约取消一经生效，不因退款失败而恢复可用或恢复占位。
- 服务收入只能由“已完成”预约贡献；已付款不等于已完成收入。

## 6. 业务规则与验收条件

### R-01 时段发布

- 店长创建时段时必须填写有效的开始和结束时间，结束时间晚于开始时间。
- 时段属于预置门店和洗护项目，容量固定为 3。
- 同一门店、同一项目的时段不得重叠，首尾相接允许。
- 已开始的时段不可新预约。
- 验收：页面可创建并查询三个未来时段；非法时间被拒绝且原因明确。

### R-02 预约唯一性与容量

- 用户只能为自己的宠物预约。
- 一个预约只对应一只宠物，时段容量按宠物数量计算。
- 同一宠物在同一时段只能存在一个有效预约。
- 待支付且未过期、已确认、取消待审核、已核销、服务中均占用名额；已完成属于已经实际使用该名额的结果记录。
- 待支付超时、待支付主动取消、取消获准后释放可继续预约的容量，且只释放一次。
- 容量检查和占位写入必须是原子操作；并发抢最后名额时最多成功到容量上限。
- 验收：并发请求后占位数不超过 3；失败请求返回“名额不足”等确定原因。

### R-03 待支付占位

- 创建预约后占位 5 分钟，并保存明确的占位截止时间。
- 超时处理必须持久化关闭结果并释放名额，不依赖用户一直停留在页面。
- 超时或支付前主动取消后不得继续正常付款确认。
- 验收：使用统一的可配置教学时钟演示超时；测试与部署演示使用同一业务规则。

### R-04 支付及晚到支付

- 支付金额固定为 9900 分，并与预约、支付请求号绑定。
- 重复支付请求和重复成功通知不得产生重复支付确认或重复金额。
- 支付成功通知在 5 分钟占位截止前被平台受理，且预约仍处于有效待支付时，预约转为已确认。
- 预约关闭后收到成功通知：记录异常、创建全额退回处理，不恢复预约、不重新占名额。
- 支付超时进入待确认，通过渠道查询或后续通知收敛，不能直接当作失败。
- 验收：正常支付、重复通知、关闭后晚到成功均有持久化结果和可查询原因。

### R-05 取消政策

- 以取消动作被平台成功受理的服务端时间和时段开始时间比较，不接受客户端自报时间作为边界依据。
- 开始前至少 2 小时（差值大于等于 2 小时）：已确认预约自动批准取消并发起全额退款。
- 开始前不足 2 小时且尚未开始：用户必须提交原因，进入待客服审核；保持占位并禁止核销。
- 客服批准：取消生效、释放名额一次、发起全额退款。
- 客服拒绝：取消申请留痕，预约恢复为可核销的已确认状态。
- 拒绝后允许重新提交新的取消申请，但同一预约同时最多存在一个待审核申请，全部申请和审核历史保留。
- 时段开始后不再允许提交本题取消申请。
- 验收：边界恰好 2 小时走自动取消；2 小时内分别演示批准和拒绝。

### R-06 退款

- 退款与取消状态独立，退款金额为原支付金额 9900 分。
- 退款成功只记账一次；重复回调不得重复累计。
- 退款失败保留失败原因并进入客服待处理列表；客服可用同一退款业务单重试，重试历史保留。
- 同一退款业务单的每次渠道尝试使用独立请求号；退款超时进入待确认，通过查询或通知收敛。
- 退款失败不能撤销已经生效的取消，也不能让预约恢复可核销状态。
- 验收：退款失败后重试成功，用户、客服和店长均能查询前后记录。

### R-07 到店核销与服务履约

- 前台只能核销本店、已确认、没有待处理取消申请且尚未核销的预约。
- 核销、服务开始、服务完成必须顺序执行并记录操作人和时间。
- 重复核销、重复开始、重复完成均返回幂等结果或明确拒绝，不重复改变金额统计。
- 验收：正常完成链路可查询；非法顺序、重复操作和非本店员工操作均被拒绝。

### R-08 取消与核销并发

- 对同一预约的取消/取消申请与核销必须使用事务、条件更新或等效并发控制。
- 最终只能出现一种合法结果：取消动作先成功则不能核销；核销先成功则不能取消。
- 不允许同时出现“已取消”和“已核销/服务中/已完成”的事实，也不允许名额或金额被重复处理。
- 验收：可重复执行并发测试，验证每次只有一个操作成功且数据一致。

### R-09 未到店

- 时段结束后，仍是已确认且未核销的预约可由店长标记未到店，并填写原因。
- 未到店不自动退款，不计为已完成服务收入。
- 用户可查看未到店结果和原因。
- 验收：结束前标记、非店长标记、非已确认预约均被拒绝。

### R-10 日清与金额核查

- 店长按业务日期和时段查看：有效预约、已完成、已取消、未到店、退款待处理。
- 至少分别展示：已收款、已退款、退款中/退款失败未退金额、已完成服务收入。
- 已收款按成功支付事实统计；已退款按成功退款事实统计；已完成服务收入仅按已完成预约统计。
- 未到店已收款单列，不计入完成服务收入，也不自动退款。
- 记录之间必须可以下钻到预约、支付、取消、退款和履约证据。
- 验收：同一天准备已服务、取消且退款成功、未到店、取消但退款失败四种记录，汇总与明细一致。

### R-11 权限和数据隔离

- 用户只可操作和查看自己的宠物、预约及资金/服务结果。
- 员工只能按角色执行本店职责；客服只能处理取消审核和退款跟进；店长查看本店经营数据。
- 所有关键写操作在服务端校验身份、门店归属、对象归属和当前状态。
- 主业务只有一家目标门店，同时预置一个外部门店员工测试身份，用于真实验证跨店拒绝。
- 验收：篡改用户、宠物、预约或门店标识不能越权。

### R-12 审计、错误与持久化

- 关键状态变化、外部回调、失败和人工操作需持久化；服务重启后可查询。
- 错误响应应给出稳定错误码和用户可理解原因，不泄露敏感信息。
- 模拟支付渠道明确标记为模拟依赖，并能受控触发成功、失败、超时/待确认和重复通知。
- 测试和教学环境可使用受控教学时钟；默认运行使用服务端时钟，页面展示当前业务时间。测试与演示使用相同规则。
- 验收：重启后业务、资金及历史仍可查；异常路径不是静态展示。

## 7. 五组端到端验收场景

| 场景 | 关键路径 | 最终核查 |
| --- | --- | --- |
| S-01 正常接待 | 发布时段→预约→支付→核销→服务开始→完成 | 用户见完成结果；店长见成功支付和完成收入 |
| S-02 名额循环 | 并发抢位→容量满→一个待支付超时/取消→新预约成功 | 容量从未超限；释放仅一次；历史仍保留 |
| S-03 取消分支 | 提前自动取消；临近取消分别批准/拒绝；退款失败后重试 | 各预约状态、名额和退款状态正确且独立 |
| S-04 现场冲突 | 同预约取消与核销并发；重复核销；跨店员工核销 | 唯一合法结果；无重复履约或金额；越权有记录 |
| S-05 收店核查 | 同日包含完成、取消退款、未到店、退款失败 | 分类数量、已收/已退/未退/完成收入与明细一致 |

## 8. 非功能与通用质量要求

- 使用 Go 实现核心业务，数据库持久化；页面覆盖用户预约订单、前台接待、客服处理和店长日清。
- 数据库统一使用 MySQL 8.0，存储引擎为 InnoDB；开发、自动测试和部署验收不得用 SQLite 替代关键并发验证。
- 金额使用整数“分”并以 `BIGINT` 保存，不使用浮点金额；数据库启用严格 SQL 模式。
- 时间以 UTC 持久化，依据门店配置时区计算和展示业务时间、取消边界与日清日期。
- 容量竞争和取消/核销竞争必须依靠数据库事务、条件更新、唯一约束、行锁或等效机制保证，不能只做“先查询再写入”。
- 自编 Go 生产代码整体及各核心业务包的单元测试语句覆盖率均不低于 85%。
- 覆盖正常、边界、非法状态、重复操作、权限、指定异常和可重复并发验证。
- 执行格式检查、`go vet`、单元测试；共享并发访问执行竞争检测。失败时不得发布。
- 正式部署必须对应 PR 合并后的 `main` 提交，并通过自动流水线门禁、健康检查和业务冒烟检查。
- 代码、日志、截图、导出会话和视频均不得包含密钥或未脱敏敏感信息。

## 9. 明确排除范围

- 优惠、优惠券、会员体系；
- 多项目、多价格、宠物档案编辑；
- 服务人员排班优化；
- 多店结算或财务会计系统；
- 真实支付渠道；
- 未到店争议退款裁决；
- 注册登录全套流程、真实短信通知和复杂后台。

这些排除项不影响角色身份可信、权限校验、完整业务分支和持久化结果要求。

## 10. 需求追踪原则

- 后续原型页面、任务、代码、测试和验收项均使用 `R-01` 至 `R-12`、`S-01` 至 `S-05` 建立对应关系。
- 未在题面明确的事项先进入假设清单；未经学生确认，不提升为正式业务规则。
