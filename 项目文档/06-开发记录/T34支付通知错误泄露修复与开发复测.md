## 原始失败

模拟支付通知投递失败时，接口直接把 `http.Client` 返回的 `err.Error()` 写入 502 响应。独立验收使用带攻击标记的不可达回调地址复现后，响应暴露了完整回调 URL、查询参数及 `dial tcp` 等底层网络细节，R-12 不通过。

## 修复内容

1. 502 响应固定为错误码 `NOTIFICATION_DELIVERY_FAILED`。
2. 对外消息固定为中文“支付结果通知发送失败，请稍后重试”。
3. 不再把渠道或网络错误文本写入 HTTP 响应。
4. 服务端日志只记录不含 URL 的支付请求号，不记录回调地址、查询参数或底层网络错误。
5. 支付、预约、退款及履约状态机均未改变。

## 新增回归测试

新增自定义 HTTP Transport，让底层错误同时包含内部主机、敏感查询标记、`dial tcp` 和自定义秘密文本，并断言 502 响应：

- 精确包含稳定错误码和中文消息；
- 不包含完整 callback URL；
- 不包含内部主机、查询标记、`dial tcp` 或底层秘密文本。

原有回调返回 500 的路径也增加相同安全响应断言。

## 运行态攻击标记复现

运行中的 Docker 服务使用以下回调地址创建模拟支付：

```text
http://127.0.0.1:1/internal-callback?token=t34-sensitive-marker
```

实际通知响应：

```json
{"error":"NOTIFICATION_DELIVERY_FAILED","message":"支付结果通知发送失败，请稍后重试"}
```

- HTTP 状态：502
- `127.0.0.1:1`：未出现
- `internal-callback`：未出现
- `t34-sensitive-marker`：未出现
- `token=`：未出现
- `dial tcp`：未出现
- 容器日志：只含 `request_no=T34-SAFE-1794470142168`
