# 题目 02——任务计划

## 1. 文档信息

- 阶段：任务规划
- 状态：待学生确认
- 计划日期：2026-11-11～2026-11-12（Europe/Berlin）
- 输入基线：已审阅需求、已确认技术选型、已确认可操作原型
- 技术栈：Gin + GORM + MySQL 8.0/InnoDB + `html/template`
- 系统形态：模块化单体 + 独立模拟支付 HTTP 服务

> 说明：以下 `Txx` 编号是仓库内部任务编号，只用于需求追踪，不能代替飞书真实需求/Bug 工作项编号。`feat`、`fix` 提交前仍须通过 `meegle` 核验教师提供的真实编号。

## 2. 阶段顺序与门禁

```text
需求与原型确认
    ↓
外部前置条件确认、MCP 建仓、dev/02 分支
    ↓
项目 AGENTS.md 与两个自编 Skill 生效
    ↓
项目骨架与数据库
    ↓
按业务闭环开发与开发自测
    ↓
独立测试 Agent → 缺陷登记 → 开发修复 → 复测
    ↓
独立验收 Agent → 问题修复 → 重新验收
    ↓
PR 门禁与合并
    ↓
main 实际提交自动部署、健康检查和业务冒烟
    ↓
证据整理、视频与当天班级群提交
```

任何门禁失败时停止进入下一阶段；修复后重新验证受影响阶段。

## 4. 开发提交建议

提交应按真实阶段和单一变更类型拆分，不能在最后一次性补造。建议的变更批次如下，但提交消息必须使用教师规范和真实工作项编号：

1. 需求、原型和任务规划材料；
2. `AGENTS.md` 与两个自编 Skill；
3. 工程骨架、配置和数据库迁移；
4. 时段与预约占位；
5. 支付与晚到支付；
6. 取消、审核与退款；
7. 核销、履约、并发控制和未到店；
8. 日清和页面；
9. 单元、集成、并发测试及覆盖率修正；
10. 验收修正、CI/CD 和交付材料。

同一个提交不得混合功能、缺陷、测试和文档类型。没有真实编号时不得提交 `feat` 或 `fix`，也不得伪装为其他类型规避。

## 5. 完成定义

单个开发任务只有同时满足以下条件才算完成：

1. 对应业务规则已实现且没有擅自扩大范围；
2. 页面或接口能够真实操作，并持久化到 MySQL；
3. 权限、非法状态、幂等和异常路径有明确结果；
4. 单元测试通过且相关核心包覆盖率不低于 85%；
5. 需要真实 MySQL 或并发行为的任务已有集成/并发验证；
6. 代码经学生检查，命令和结果真实保存；
7. 文档、代码、测试和需求编号建立追踪；
8. 失败后已修复并重新执行受影响检查。
