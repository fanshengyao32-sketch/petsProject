## 7. 缺陷、观察项与纠正记录

以下 `T31-DEF-*`、`T31-OBS-*`、`T31-CORR-*` 仅为本报告内部索引，不冒充真实飞书 Bug 编号；只有 `DEF-01` 是当前阻断缺陷。

### T31-DEF-01（阻断）：占位过期后台任务与预约事务发生 InnoDB 死锁，1213 未重试/未映射

- 关联：R-02、R-03、R-08、R-12、S-02。
- 最小复现命令：配置五个真实 MySQL DSN 后执行 `go test -count=5 ./...`。
- 期望：四人抢三个名额时 3 个成功、1 个稳定返回 `ErrCapacityFull`；后台过期任务不得令正常业务返回数据库内部错误。
- 实际：测试收到 `Error 1213 (40001): Deadlock found when trying to get lock; try restarting transaction`。
- HTTP 表现：同一全量交互中，宠物越权用例曾由期望 403 波动为 500；重复预约场景也曾出现首次操作未成功、第二次反而成功。
- 数据库事实：`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 指向 `pet_booking_t31_booking`：
  - 事务 1 执行全局 `UPDATE bookings ... WHERE status='pending_payment' AND hold_expires_at <= 当前时间 ...`，持有 `idx_bookings_hold_expiry` 锁并等待 `service_slots.PRIMARY`；
  - 事务 2 持有 `service_slots.PRIMARY` 排他锁，执行带 `slot_id=1` 的过期更新并等待 `idx_bookings_hold_expiry`；
  - MySQL 回滚事务 2。
- 根因定位证据：`cmd/server` 包测试通过同一个 `MYSQL_TEST_DSN` 启动过期 worker，而 booking 包并行执行预约事务，复现生产中后台清理与请求并发的锁顺序冲突。`CreateBooking`/`ExpireHolds` 未对 1213 做有界重试，也未转成稳定业务错误。
- 数据结果：被回滚事务不会产生超额占位，但调用结果不满足“确定原因”和可重复并发门禁，故仍是阻断缺陷。

### T31-CORR-02（已纠正，不是缺陷）：曾误判覆盖率门禁不满足

- 关联：通用测试要求、AGENTS 第 7 节。
- 初稿误判：因 `auth 83.6%`、`platform/database 84.0%`、`platform/httpserver 63.6%`、`cmd/server 80.0%`，初稿将本项列为阻断，并要求所有辅助包单包达到 85%。
- 纠正依据：门禁要求的是整体和每个核心业务包达到 85%；Handler/Repository 不得排除是整体统计范围要求，不是新增逐辅助包阈值。
- 正确结论：整体 85.7%；五个核心业务包为 85.2%～87.6%，全部通过；上述辅助包均已纳入整体统计。因此覆盖率门禁 **PASS**，不要求为了本次门禁将辅助包各自补到 85%。

### T31-OBS-03（环境/门禁问题，不是源代码格式缺陷）：Windows 换行转换令工作树 `gofmt -l` 失败

- 关联：AGENTS 第 7 节、发布质量门禁。
- 复现：`gofmt -l -e .`。
- 实际：53 个 Go 文件全部被列出；差异表现为整文件 CRLF→LF。
- 反证：逐个读取 `HEAD` 中 53 个 Go blob，经 `gofmt` 后重新计算 Git 对象哈希，`BLOB_GOFMT_MISMATCH=0`。因此固定提交本身已经格式化，不能要求开发 Agent 为此改写生产代码。
- 要求：调整 Windows checkout/门禁方式，例如在 CI 的 LF checkout 上检查，或直接比较 Git blob 的 `gofmt` 结果；之后重跑门禁并保留该环境说明。

### T31-OBS-04（中风险观察，非当前阻断）：模拟支付通知失败直接返回底层错误文本

- 关联：R-12、安全错误和敏感信息要求。
- 位置：`cmd/mock-payment/main.go` 的 `triggerNotification` 将 `sendNotification` 的 `err.Error()` 直接放入 HTTP JSON。
- 风险：网络/URL/下游错误可能向调用方暴露内部地址或实现细节，且不属于稳定业务错误码。
